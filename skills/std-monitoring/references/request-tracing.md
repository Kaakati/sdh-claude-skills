# Request Tracing — one id, end to end

Load-bearing rules restated (hold even if you read nothing else):

1. **Rails already generates the id.** `ActionDispatch::RequestId` is in the default middleware
   stack — you do not build this, you *propagate* it.
2. **The trace breaks at the async boundary.** A Sidekiq job knows nothing about the request that
   enqueued it unless you pass the id explicitly. That is where the id is needed most.
3. **`Current` is per-thread and must be reset**, or a request inherits the previous request's id
   on a reused thread.

---

## Why this file exists

`SKILL.md` says *"every log entry must include `request_id`"*, `std-api-design` puts it in the
error envelope, and `log-search` builds its whole "trace one request" workflow on it. **Eleven
files depend on this id and none of them said where it comes from.** This one does.

**No hook checks for it, deliberately.** `monitoring-checker.py` used to warn when a log line did
not literally contain `request_id`, and that check was removed: the id is attached by Rails via
`config.log_tags`, so it is **not in the source line at all**. On a correctly configured app every
plain `Rails.logger.info("…")` was a false positive, and on a misconfigured one no amount of
per-call editing fixes it — the remedy is the one line of config below. A rule satisfied by config
is not a per-call warning. So the id's presence is **your configuration's job, not a gate's**,
which is exactly why this file has to be right.

## What Rails gives you for free

From the API docs, `ActionDispatch::RequestId`:

> *"Makes a unique request id available to the `action_dispatch.request_id` env variable (which is
> then accessible through `ActionDispatch::Request#request_id` or the alias
> `ActionDispatch::Request#uuid`) and sends the same id to the client via the `X-Request-Id`
> header."*

And crucially:

> *"The unique request id is either based on the `X-Request-Id` header in the request, which would
> typically be generated by a firewall, load balancer, or the web server, or, if this header is
> not available, a random uuid. If the header is accepted from the outside world, we sanitize it
> to a max of 255 chars and alphanumeric and dashes only."*

Two consequences worth internalising:

- **The ALB's trace id flows straight through.** If your load balancer sets `X-Request-Id`, Rails
  adopts it, so the id in your logs is the same one in the LB's logs. That is a free join across
  two systems.
- **It is outside input, and Rails knows it.** The sanitisation exists because a client can send
  this header. Never interpolate a request id into SQL or a shell command on the assumption that
  it is "internal" — it is 255 chars of attacker-influenced text with a friendly name.

## Step 1 — tag every log line (one line of config)

```ruby
# config/environments/production.rb  ✅
# `config.log_tags` "accepts a list of methods that the request object responds to". The
# request responds to `request_id`, so every line in this request is prefixed with it —
# including lines from code that has no idea a request exists.
config.log_tags = [:request_id]
```

That alone makes `filter ctx.request_id = "…"` work in Logs Insights
(`../log-search/references/cloudwatch-insights.md`). Everything below is about the places tags
do **not** reach.

## Step 2 — make the id reachable outside the controller

Log tags decorate log lines. They do not give your *service objects* the id to put into a
structured payload, a Centrifugo message, or a job.

```ruby
# app/models/current.rb  ✅
class Current < ActiveSupport::CurrentAttributes
  attribute :request_id, :user_id
end
```

```ruby
# app/controllers/application_controller.rb  ✅
class ApplicationController < ActionController::API
  before_action :set_current_context

  private

  def set_current_context
    # CurrentAttributes is reset by Rails between requests via an executor hook — that reset
    # is the whole reason to use it instead of a bare Thread.current, which on a reused
    # Puma thread would hand request N the id from request N-1.
    Current.request_id = request.request_id
    Current.user_id    = current_user&.id
  end
end
```

Now anything, at any depth, can say `Current.request_id` without threading it through five
method signatures.

## Step 3 — the async boundary, where the trace actually breaks

**This is the part everyone misses, and it is the part that matters.** A Sidekiq job runs in a
different process, minutes later. It has no request. `Current.request_id` is `nil`. So the job's
logs — the ones you are hunting at 3am, because the async work is what failed — have no id, and
the trace stops precisely where the incident starts.

### Bad — the trace dies at `perform_async`

```ruby
# app/services/orders/create.rb  ❌
class Orders::Create
  def call
    order = Order.create!(**attrs)
    Rails.logger.info({ msg: "order created", order_id: order.id })  # tagged: has the id
    OrderConfirmationJob.perform_async(order.id)                      # the id stops HERE
    order
  end
end
```

```ruby
# app/jobs/order_confirmation_job.rb  ❌
class OrderConfirmationJob
  include Sidekiq::Job

  def perform(order_id)
    # No request, no Current, no tag. This log line is an orphan: you can see it failed,
    # and you cannot tie it to the request that caused it.
    Rails.logger.info({ msg: "sending confirmation", order_id: })
    # ...
  end
end
```

### Good — carry the id across the process boundary

```ruby
# config/initializers/sidekiq.rb  ✅
module SidekiqTracing
  # Runs in the WEB process when the job is enqueued: stamps the current request's id into
  # the job payload.
  class Client
    include Sidekiq::ClientMiddleware

    def call(_worker_class, job, _queue, _redis_pool)
      job["request_id"] ||= Current.request_id
      yield
    end
  end

  # Runs in the WORKER process when the job executes: restores it.
  class Server
    include Sidekiq::ServerMiddleware

    def call(_worker, job, _queue)
      Current.request_id = job["request_id"]
      # Re-tag the logger too, so plain Rails.logger calls inside the job carry the id
      # without every job author remembering to add it.
      Rails.logger.tagged(job["request_id"]) { yield }
    ensure
      Current.request_id = nil    # the worker thread is reused — leaking the id would
                                  # mislabel the NEXT job, which is worse than no id at all
    end
  end
end

Sidekiq.configure_client do |config|
  config.client_middleware { |chain| chain.add SidekiqTracing::Client }
end

Sidekiq.configure_server do |config|
  config.client_middleware { |chain| chain.add SidekiqTracing::Client }  # jobs enqueuing jobs
  config.server_middleware { |chain| chain.add SidekiqTracing::Server }
end
```

Note `configure_server` registers the **client** middleware too: a job that enqueues another job
must pass the id along, or the trace dies one hop later instead of immediately.

The `ensure` is not defensive padding. Sidekiq reuses threads; without the reset, job N+1
inherits job N's id and your trace confidently points at the wrong request.

## Step 4 — the id leaves the building

```ruby
# The API response already carries it — ActionDispatch::RequestId "sends the same id to the
# client via the X-Request-Id header". So a mobile bug report that includes the header is
# directly greppable in CloudWatch. Put it in your error envelope too:
render json: { error: { code: "FORBIDDEN", request_id: Current.request_id } }, status: :forbidden
```

The envelope's shape is owned by `../std-api-design/references/errors-rails.md` — the point here
is only that the id belongs in it, so a user screenshot becomes a log query.

```ruby
# Centrifugo: SKILL.md requires the id on real-time messages, for the same reason —
# otherwise a push that never arrived cannot be tied to the request that triggered it.
Centrifugo.publish("orders:#{user_id}", { type: "order.created", order_id:, request_id: Current.request_id })
```

## Verifying it end to end

Do not assume it works because the config is present. Prove it once:

```bash
# Send your own id in, and check it comes back and lands in the logs.
curl -si -H "X-Request-Id: trace-me-12345" https://api.example.com/api/v1/orders | grep -i x-request-id
```

Then, in the log tool, ask for **every line** for `trace-me-12345` across the web *and worker*
log groups (`../log-search`). If the job's lines are missing, step 3 is not wired — and you have
just learned that during a drill rather than during an incident.

> **What not to log.** The id is safe; the request is not. `std-security` owns this, but it bears
> repeating where tracing is discussed: tags make it tempting to log the whole `params` hash "for
> context". That is how passwords and tokens reach CloudWatch, where they are retained,
> searchable, and out of your control. `config.filter_parameters` is the floor, not the ceiling.
